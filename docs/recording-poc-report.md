## 2. 録音方式・保存形式

`joinVoiceChannel` の `selfDeaf:false`、`selfMute:true`、`daveEncryption:true` を指定します。開発チーム用テストでは同意操作を求めず、準備通知後に接続します。DAVE交渉とnativeセッションの鍵準備を確認し、開始通知後にユーザー別 `VoiceReceiver.subscribe` をManualで購読します。実際の受信経路を実装しており、モックへの置換はしていません。自動テストのみ接続アダプターを差し替えます。

標準Opus無音終端を除き、実Opusデコーダーの出力を逐次ファイルへ保存します。48kHz / 2ch / PCM signed 16bit LE / WAVを選びました。コンテナとPCMを単純に扱えて一般的なプレーヤーで検査でき、サンプル数から音声長を計算できるためです。容量は192,000 bytes/秒で、15分の連続発言は話者1人約173MBです。

WAVは `.partial` に書き、終了時に完了済みPCM長でtruncate・ヘッダー確定・sync・close・renameします。容量とユーザー別の書き込み待ちバッファを制限します。途中appendの余剰末尾も確定時に除きます。保存障害で回収できないファイルは不完全として記録します。

## 3. 音声とユーザーIDの紐付け

SSRCからユーザーIDへの対応はライブラリの `receiver.ssrcMap` がWebSocketの対応更新・削除を管理します。対象ユーザーIDを指定した購読だけが保存処理へ渡り、受信時にも対応の存在を確認します。未知の対応は保存しません。SSRCを直接固定したり、自分でRTPを復号したりしません。

2026-10-09の依頼に合わせ、`/record consent`、同意待ち・撤回処理、`CONSENT_TIMEOUT_MS` を削除しました。初期参加者・途中参加者・再参加者は自動で録音対象となります。参加者変更時は同期的に全ユーザー購読を停止し、通知・確定処理後に再開します。この間の音声は保存しません。ギルドごとのMapと保存ディレクトリにより状態とファイルを分離します。ユーザーID・参加履歴は機密メタデータとして保存し、コンソールには出しません。新規メタデータは `schemaVersion: 2` とし、同意フィールドを保存しません。混合CLIが利用する時刻・セグメント形式は同じため、旧形式の終了済みセッションも再出力できます。

## 4. 時刻同期と精度の限界

初回録音開始時に壁時計と単調時計の基準を持ちます。セグメント開始は最初の復号後パケット到着時刻−デコード音声長、終了は開始＋累積PCMサンプル時間です。可変長の10/20/40/60ms音声でサンプル数を確認しました。

標準無音終端・パケットの長い空白・80msを超える間隔異常または累積ドリフトで分割し、混合時に48kHzのサンプル位置へ丸めて配置します。同時発言は別ファイルと重なる時刻区間のまま保存します。会議全体の空白を単純連結して詰めません。混合は1秒ブロック、固定ゲイン1/音声保存ユーザー数で加算し、残るクリップ数を記録します。

これは到着時刻による**推定**です。送信元時計、RTP timestamp、連番、ジッターバッファを公開受信ストリームから取得していません。最初のパケット境界、ネットワーク遅延差、順序逆転、80ms以下の欠落/ドリフトは完全に復元できません。ネットワークジッターで誤分割・区間重複も生じ得ます。サンプル位置への丸め精度約0.021msはネットワーク由来の同期精度を保証しません。

## 7. 発見した不具合と対応

| 再現条件 | 発見事項 | 対応 |

## 8. 既知の制約・残課題

- [voiceの公式説明](https://discord.js.org/docs/packages/voice/0.19.2) が示す通り、Discordの音声受信は未文書化で安定保証がありません。SSRC管理、復号、購読ストリーム、再接続の挙動は配布バージョンに依存します。
- DAVEの交渉/鍵確認に公開型のnetworking/daveを使用しています。ライブラリの変更時は再評価が必要です。第11節の診断ではDAVEのdebug失敗通知を接続全体で集計しますが、ユーザー別の正確な失敗数やパケットロス率は得られません。
- Ready復帰だけでMLS鍵が準備済みとは限りません。初回は鍵を待ち、受信時に鍵が使えなければ安全側で失敗します。実環境のDAVE遷移・再接続・音声欠落は未検証です。
- 受信0件を無言と受信失敗に自動分類しません。statusと既知の発言合図で確認してください。
- VAD、FEC、RTP順序補正、欠落音声の補完はありません。マイク回り込みを防ぐ保証もありません。
- 最大15分・512MiB・ユーザー別4MiB待ちキューを既定とします。多人数、長時間、複数ギルド同時でのCPU・ディスク速度・メモリ推移は未検証です。停止後の混合出力にも追加容量と処理時間が必要です。
- native Opusは参照解放後にGCで破棄されます。即時nativeメモリ返却は保証できず、多数回のセグメント/再接続で観測が必要です。
- SIGKILL・電源断・保存先障害に対する自動回収/再開はありません。`.partial`、`complete:false`、古いcheckpointを正常な完了結果として扱わないでください。
- 開発チームのテスト用として同意操作を削除しています。開始・停止・参加者変更の公開通知と許可ギルド制限は維持します。停止・退出後も受信済みキューと過去分は保持し、削除は管理者によるセッション全体削除です。

## 11. 複数ユーザー録音の不具合調査（2026-10-10）

### 調査結果と確度

報告された症状は「最初に発言したユーザーだけ正常で、それ以外の録音は0秒表示」です。今回の実Discordでの再現は未実施です。既存の2セッションを読み取り専用で検査し、実ユーザーID・音声内容は出力せず、保存データは変更・削除していません。

録音済みの1セッションでは、5人中3人にそれぞれ1,318 / 551 / 1,298パケット、保存PCMは23.18 / 8.10 / 24.28秒あり、残る2人はパケット・セグメントとも0でした。69個すべての個別WAVをPython `wave`で検査し、48kHz・2ch・16bit、メタデータのサンプル数・実サイズ・ヘッダーが一致しました。空のWAVは0個、1秒未満は54個、最短60ms・最長7,540msです。もう1セッションは録音開始前に終了し、音声ファイルがありません。

この成果物は「全員のファイルが空」「常に最初の話者しか保存できない」という状況を示してはいません。プレーヤーによる短い区間の秒表示丸めは候補ですが、表示・聴取は今回未確認です。パケット0の2人については、Opusデコードや保存に入る前からデータが届いていません。ただし、無言・ミュート・SSRC未登録・UDP未到着・DAVE失敗・購読不整合のどれかは旧メタデータだけでは判別できません。

利用中の `node_modules/@discordjs/voice/dist/index.js`（0.19.2）と型定義を確認しました。最新mainのコードを修正根拠としていません。受信は `onUdpMessage` → SSRCの数値検索 → ユーザー別subscriptions → 輸送復号 → `DAVESession.decrypt` → `stream.push` です。`ssrcMap.get(userId)`は0.19.2でも対応する公開APIで、正常パケットを一律破棄する誤用は確認されませんでした。ユーザー別購読、UserCapture、native Opusデコーダー、書き込みキューは独立しています。nativeデコーダーはPCMをコピーして返す実装でした。混合は1/音声保存人数の固定ゲインで小さくなり得ますが、個別WAVを0秒にする処理ではありません。
