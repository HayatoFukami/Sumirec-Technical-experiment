## 2. 録音方式・保存形式

`joinVoiceChannel` の `selfDeaf:false`、`selfMute:true`、`daveEncryption:true` を指定します。開発チーム用テストでは同意操作を求めず、準備通知後に接続します。DAVE交渉とnativeセッションの鍵準備を確認し、開始通知後にユーザー別 `VoiceReceiver.subscribe` をManualで購読します。実際の受信経路を実装しており、モックへの置換はしていません。自動テストのみ接続アダプターを差し替えます。

標準Opus無音終端を除き、実Opusデコーダーの出力を逐次ファイルへ保存します。48kHz / 2ch / PCM signed 16bit LE / WAVを選びました。コンテナとPCMを単純に扱えて一般的なプレーヤーで検査でき、サンプル数から音声長を計算できるためです。容量は192,000 bytes/秒で、15分の連続発言は話者1人約173MBです。

WAVは `.partial` に書き、終了時に完了済みPCM長でtruncate・ヘッダー確定・sync・close・renameします。容量とユーザー別の書き込み待ちバッファを制限します。途中appendの余剰末尾も確定時に除きます。保存障害で回収できないファイルは不完全として記録します。

## 3. 音声とユーザーIDの紐付け

SSRCからユーザーIDへの対応はライブラリの `receiver.ssrcMap` がWebSocketの対応更新・削除を管理します。対象ユーザーIDを指定した購読だけが保存処理へ渡り、受信時にも対応の存在を確認します。未知の対応は保存しません。SSRCを直接固定したり、自分でRTPを復号したりしません。

2026-10-09の依頼に合わせ、`/record consent`、同意待ち・撤回処理、`CONSENT_TIMEOUT_MS` を削除しました。初期参加者・途中参加者・再参加者は自動で録音対象となります。参加者変更時は同期的に全ユーザー購読を停止し、通知・確定処理後に再開します。この間の音声は保存しません。ギルドごとのMapと保存ディレクトリにより状態とファイルを分離します。ユーザーID・参加履歴は機密メタデータとして保存し、コンソールには出しません。新規メタデータは `schemaVersion: 2` とし、同意フィールドを保存しません。混合CLIが利用する時刻・セグメント形式は同じため、旧形式の終了済みセッションも再出力できます。

## 4. 時刻同期と精度の限界

初回録音開始時に壁時計と単調時計の基準を持ちます。セグメント開始は最初の復号後パケット到着時刻−デコード音声長、終了は開始＋累積PCMサンプル時間です。可変長の10/20/40/60ms音声でサンプル数を確認しました。

標準無音終端・パケットの長い空白・80msを超える間隔異常または累積ドリフトで分割し、混合時に48kHzのサンプル位置へ丸めて配置します。同時発言は別ファイルと重なる時刻区間のまま保存します。会議全体の空白を単純連結して詰めません。混合は1秒ブロック、固定ゲイン1/音声保存ユーザー数で加算し、残るクリップ数を記録します。

これは到着時刻による**推定**です。送信元時計、RTP timestamp、連番、ジッターバッファを公開受信ストリームから取得していません。最初のパケット境界、ネットワーク遅延差、順序逆転、80ms以下の欠落/ドリフトは完全に復元できません。ネットワークジッターで誤分割・区間重複も生じ得ます。サンプル位置への丸め精度約0.021msはネットワーク由来の同期精度を保証しません。

## 7. 発見した不具合と対応

| 再現条件 | 発見事項 | 対応 |
|---|---|---|
| 既存opusscript 0.1.1で10/20/40/60msのステレオ音を連続encode/decode | WASM `memory access out of bounds`。後続デコーダー初期化も失敗 | @discordjs/opusへ変更。同じ可変長テストで成功。opusscriptを依存から削除 |
| @discordjs/opusをnamed importしたビルド出力をNode.js ESMで直接起動 | `Named export 'OpusEncoder' not found`（Vitestでは通る） | CommonJS対応のTypeScript `import = require` に変更し、ビルド後のNode.js読み込みを確認 |
| 購読破棄と同じtick内に同じユーザーへ再購読 | ライブラリのsubscriptions Mapが旧destroy済みストリームを返す可能性 | 旧ストリームのclose後に再購読し、自動テストで確認 |
| WAV appendが途中で失敗し末尾だけ書けた場合 | 完了済みPCM長と実ファイル長がずれる可能性 | 確定時に完了済み長へtruncateするテストを追加 |
| 準備・開始通知待機中の停止、開始通知待機中の途中参加 | 非同期処理から戻った後に停止済みの録音を開始したり、変更前の参加者への通知で受信を開始する可能性 | 通知後の状態・参加者変更番号を再確認し、3つの競合テストで確認 |

## 8. 既知の制約・残課題

- [voiceの公式説明](https://discord.js.org/docs/packages/voice/0.19.2) が示す通り、Discordの音声受信は未文書化で安定保証がありません。SSRC管理、復号、購読ストリーム、再接続の挙動は配布バージョンに依存します。
- DAVEの交渉/鍵確認に公開型のnetworking/daveを使用しています。ライブラリの変更時は再評価が必要です。第11節の診断ではDAVEのdebug失敗通知を接続全体で集計しますが、ユーザー別の正確な失敗数やパケットロス率は得られません。
- Ready復帰だけでMLS鍵が準備済みとは限りません。初回は鍵を待ち、受信時に鍵が使えなければ安全側で失敗します。実環境のDAVE遷移・再接続・音声欠落は未検証です。
- 受信0件を無言と受信失敗に自動分類しません。statusと既知の発言合図で確認してください。
- 録音中のVAD、FEC、RTP順序補正、欠落音声の補完はありません。停止後の非破壊VAD分類は第13節を参照してください。マイク回り込みを防ぐ保証もありません。
- 最大15分・512MiB・ユーザー別4MiB待ちキューを既定とします。多人数、長時間、複数ギルド同時でのCPU・ディスク速度・メモリ推移は未検証です。停止後の混合出力にも追加容量と処理時間が必要です。
- native Opusは参照解放後にGCで破棄されます。即時nativeメモリ返却は保証できず、多数回のセグメント/再接続で観測が必要です。
- SIGKILL・電源断・保存先障害に対する自動回収/再開はありません。`.partial`、`complete:false`、古いcheckpointを正常な完了結果として扱わないでください。
- 開発チームのテスト用として同意操作を削除しています。開始・停止・参加者変更の公開通知と許可ギルド制限は維持します。停止・退出後も受信済みキューを確定します。新規録音の自動削除は廃止しました（第13節）。管理者への過去分の削除依頼は、管理者によるセッション全体削除です。

## 11. 複数ユーザー録音の不具合調査（2026-10-10）

### 調査結果と確度

報告された症状は「最初に発言したユーザーだけ正常で、それ以外の録音は0秒表示」です。今回の実Discordでの再現は未実施です。既存の2セッションを読み取り専用で検査し、実ユーザーID・音声内容は出力せず、保存データは変更・削除していません。

録音済みの1セッションでは、5人中3人にそれぞれ1,318 / 551 / 1,298パケット、保存PCMは23.18 / 8.10 / 24.28秒あり、残る2人はパケット・セグメントとも0でした。69個すべての個別WAVをPython `wave`で検査し、48kHz・2ch・16bit、メタデータのサンプル数・実サイズ・ヘッダーが一致しました。空のWAVは0個、1秒未満は54個、最短60ms・最長7,540msです。もう1セッションは録音開始前に終了し、音声ファイルがありません。

この成果物は「全員のファイルが空」「常に最初の話者しか保存できない」という状況を示してはいません。プレーヤーによる短い区間の秒表示丸めは候補ですが、表示・聴取は今回未確認です。パケット0の2人については、Opusデコードや保存に入る前からデータが届いていません。ただし、無言・ミュート・SSRC未登録・UDP未到着・DAVE失敗・購読不整合のどれかは旧メタデータだけでは判別できません。

利用中の `node_modules/@discordjs/voice/dist/index.js`（0.19.2）と型定義を確認しました。最新mainのコードを修正根拠としていません。受信は `onUdpMessage` → SSRCの数値検索 → ユーザー別subscriptions → 輸送復号 → `DAVESession.decrypt` → `stream.push` です。`ssrcMap.get(userId)`は0.19.2でも対応する公開APIで、正常パケットを一律破棄する誤用は確認されませんでした。ユーザー別購読、UserCapture、native Opusデコーダー、書き込みキューは独立しています。nativeデコーダーはPCMをコピーして返す実装でした。混合は1/音声保存人数の固定ゲインで小さくなり得ますが、個別WAVを0秒にする処理ではありません。

| 未確定 | 報告されたDiscordセッションで実際にどの段階が失敗したか。既存成果物に今回の診断がなく確定不可 | 診断を有効にした実Discord再録音で切り分ける |

### 移動の安全性・障害復旧

移動予定を `vad.moves[].pending` としてatomic保存・syncしてから、同一セッション内へhard linkを排他的に作成します。WAVのdevice/inode/sizeと64KiB逐次SHA-256で全バイト一致を確認し、移動先sync後に元の名前だけを解除します。正常終了時の重複コピーはありません。途中停止では両方の名前が同じinodeを指す場合があり、音声本体を失わずに復旧できます。宛先衝突、symlink、変更された内容、同じ元/先パス・重複ジャーナルは拒否します。保存記録が未解決ならmixを保留します。

同一セッションの同時実行はプロセス内ガード＋ `.vad.lock` のO_EXCLで拒否します。SIGKILL等でロックが残ったら、管理者がBot/CLIの停止を確認して `.vad.lock`だけを解除し、`pnpm recover-vad <guildId> <sessionId>` を実行します。復旧は保存済みpendingのみ、再推論や過去録音の新規分類は行いません。2つの名前があれば同一性を照合し、先だけなら内容を照合して参照を更新します。旧 `silenceCleanup`を変更・自動復旧しません。旧 `recover-silence`は存在する予定WAVを削除するため、その挙動をREADMEへ明記しました。

管理者専有の0700保存先・信頼できる親ディレクトリ・他者が保存先を差し替えないことを前提にします。NodeのパスベースAPIだけで、特権を持つ別プロセスによる同時ディレクトリ差し替えを完全防御するものではありません。hard linkに対応する同一ローカルファイルシステムを使用し、POSIXではディレクトリsyncも必要です。WindowsのACL・ディレクトリ同期の制約は第14節を参照してください。実電源断・保存媒体障害は未検証で、音声やmetadata自体の損失は復元できません。VAD記録保存前の強制終了から自動分類を再開する機能や、録音partialの修復はありません。

## 14. Windowsの録音準備失敗・Opusの型参照修正（2026-10-11）

### 原因と修正

ユーザーのWindows PowerShellログに `src/capture.ts:13 TS2503: Cannot find namespace 'Opus'` があり、ローカルの `pnpm typecheck` でも再現しました。直前のESM対応で `createRequire` の返り値を `Opus` という値へ代入した後、`Opus.OpusEncoder` を型の名前空間として参照したのが原因です。配布済み0.10.0の型定義を確認し、`import type { OpusEncoder }` に分離しました。実行時のCommonJS読込は維持し、可変長実Opusテストに終了後のデコード拒否・連続終了も追加しました。`pnpm start` は `dist/` を直接実行するため、ビルド失敗後の `bot_ready` は最新ソースのビルド成功の証拠ではありません。

「録音準備に失敗しました」の処理経路には、公開準備通知・音声接続より前の `atomicJson → syncDirectory` がありました。従来は全OSでディレクトリを `O_RDONLY | O_DIRECTORY | O_NOFOLLOW` で開き、syncしていました。[Node.jsのファイルフラグ仕様](https://nodejs.org/api/fs.html#file-system-flags)ではWindowsに `O_DIRECTORY` / `O_NOFOLLOW` は提供されません。[libuvのWindows実装](https://github.com/libuv/libuv/blob/v1.x/src/win/fs.c)のfsyncは `FlushFileBuffers` を使い、[MicrosoftのAPI要件](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers)ではhandleに書き込み権限が必要です。読み取り専用ディレクトリのsyncはこの要件を満たせず、初回メタデータ保存を失敗させます。提示ログに内部エラーがないため、ユーザーの実環境で同じ原因だったことは未確認ですが、開始前に失敗するWindows非対応の実装を特定・修正しました。

`src/storage.ts` はWindowsでディレクトリの実在・通常ディレクトリ・symlinkでないことを検査してからディレクトリsyncだけを省きます。ファイル自身のsync、rename、WAV確定、VAD分類・移動、混合生成と、それらのエラー検出は維持します。POSIXのディレクトリsync失敗は従来どおり伝播します。`src/session.ts` は準備失敗を `storage_directory_error` / `metadata_write_error` / `start_notification_error` に分け、返信とメタデータへ固定コードを残します。外部例外本文やパスを公開しません。録音方式・ユーザー紐付け・時刻推定・DAVEは変更していません。

| G9 再実行・設定変更・上限・dry-run | 自動検証達成 | 同設定再送0、設定変更再送、設定を戻した再利用、要求/秒数上限 |
| G10 型・テスト・ビルドと実API状況記録 | 達成 | 上記3コマンド成功、実API未実施の理由を本節へ記録 |
